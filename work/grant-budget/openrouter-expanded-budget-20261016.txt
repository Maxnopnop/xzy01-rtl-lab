RESEARCH QUESTION AND MODEL ROLES
Investigate whether explicit timing representations and executable feedback improve generated RTL under matched call opportunities, and which observable stage contains an error.
Sol retains a model-family link to earlier development, without claiming backend equivalence to the Codex login route.
Claude and Gemini test whether findings extend across model developers, rather than only within two OpenAI variants.
Three candidates replace the earlier two-model costing scenario; proposal's two/four-model inconsistency needs supervisor reconciliation. Model availability, exact endpoint, and supported controls must be checked before protocol freeze. Preview retirement requires a revised, recorded selection before evaluation, not silent switching during a batch.

EXPERIMENTAL DESIGN
Target: 20 development tasks and 80 held-out evaluation tasks, reviewed for provenance, compatible timing contracts, reference correctness, and near duplicates.
80 held-out tasks are NOT currently established or frozen. This is a feasibility-dependent expansion from the earlier 40-task planning estimate.
Suggested strata: reset/priority, state transitions, cycle latency, and ready/valid transaction ordering; target 20 tasks per stratum subject to admissibility, without filling gaps with near-duplicates.
For each model/task/repetition, four strategy paths:
S-F: structured timing representation -> RTL -> revision with public executable feedback.
S-R: same representation and RTL parent -> regeneration without execution feedback.
D-F: direct RTL -> unconditional no-feedback revision -> revision with public executable feedback.
D-R: same direct RTL and revision parent -> regeneration without execution feedback.
Each final path has 3 model-call opportunities. Each representation branch shares the first two calls between F/R, then has two distinct third calls: 4 actual calls per representation, 8 actual calls overall.
The first direct RTL output also supplies the single-call baseline without extra API calls.
No best-of selection; final scoring uses hidden tests only after generation. Public feedback availability and design facts matched across representation conditions.
This compares workflows; equal calls do not imply equal tokens, FLOPs, or identical intermediate semantics. Report input/output/reasoning/cache separately without double counting.
Keep fixed planned call opportunities irrespective of intermediate functional success; infrastructure failure invokes the stopping policy. Negative and truncated results stay visible.

CALL PLAN
Development: 20 tasks x 2 repetitions x 3 models x 8 actual calls = 960.
Held-out main evaluation: 80 x 5 x 3 x 8 = 9,600.
Wording robustness: 40 semantic-preserving variants x 3 x 3 x 8 = 2,880.
Variants are paired with 40 preselected held-out originals and compare against those originals' first 3 repetitions. They are NOT 40 additional independent tasks. Review/freeze variants before model outcomes, with no tuning on them.
Core total = 13,440 actual calls; 4,480 per model.
Technical retry ceiling = 5% = 672 attempts, at most 224/model; at most one retry per eligible documented transient infrastructure failure.
Total attempt ceiling = 14,112, not 13,440 plus open-ended retries.
A wrong or malformed answer is not eligible for a technical retry. Reconcile unknown billing before retrying. Stop for persistent service errors or any cost/token cap breach.
Statistical analysis pairs conditions by task and clusters repetitions/variants at original task (and source family where appropriate). Five repetitions measure variation but do not guarantee power; no claimed minimum detectable effect yet.

TOKEN AND COST ENVELOPE
Planning envelope per actual call: at most 12,000 input tokens and 6,000 billed output tokens including reasoning, subject to provider enforcement validation during development.
The output allowance is NOT a measured mean. Earlier Codex R6 averaged about 11,395 input and 934 output tokens, including reasoning, on a narrower workload. A higher allowance is provisional for different reasoning models and more complex temporal tasks; calibrate it before main evaluation.
No artificial prompt padding or minimum-output requirement. Store actual usage and stop/shrink scope if limits are unsuitable; do not claim savings require extra calls.
Per model core token allowance: 53.76M input + 26.88M billed output.
Conservative input accounting: Sol and Claude at USD 5/M short cache-write rate, with no cache-read discount; Gemini at ordinary USD 2/M with no explicit cache storage purchased. APPLICATION JUSTIFICATION (ENGLISH)
We propose an API spending ceiling of HKD 19,500 for a controlled study using GPT-5.6 Sol, Claude Opus 5.5, and Gemini 3.1 Pro Preview through OpenRouter. The planned scope comprises 20 development tasks, 80 held-out tasks with five repeated trials, and 40 paired specification variants. Four conditions will separate the effects of structured timing representations and executable feedback, while shared generation steps limit the core workload to 13,440 API calls. The three model families assess generalisability, repeated trials quantify variability, and paired variants test robustness to wording. The ceiling uses published token rates, allowances of up to 12,000 input and 6,000 billed output tokens per call, a 5.5% platform fee, and bounded retry and price/exchange reserves. Task availability and token needs will be validated before the main study, and spending will be reduced where appropriate. Results will support the demonstration prototype and reproducible research package. Existing available funding will be deducted from the additional grant request.
